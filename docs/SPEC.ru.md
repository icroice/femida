# Femida — спека (v2)

> Статус: черновик 0.1 (2026-11-24). Спека живёт в репо (решение v2-1) и
> является источником правды: код и спека меняются одним изменением,
> рассинхрон — баг. Решения нумеруются `v2-N` и только добавляются.
>
> v1 (QA-evidence сервис) опубликована; её функционал целиком переезжает
> в модуль `qa` (§4). Контракты REST/MCP v1 публичные — ломающие изменения
> только отдельным решением.

## 1. Концепция

Femida v2 — самохостимый таск-трекер с канбан-доской, построенный как
модульная платформа. Ядро владеет пользователями, проектами, ролями и
доской; вся функциональность живёт в подключаемых модулях. QA-прогоны v1 —
первый модуль, а не весь продукт.

**Состав v2.0** (решение v2-9): ядро + доска + шесть модулей-стадий +
перенос QA + MCP-инструменты задач + REST v2 (запись) + комментарии в
задачах + уведомления + дашборд проекта. Интеграции: только статусы
pull request (модуль `dev`); импорт задач извне — после v2.0. Спринтов
нет (v2-10): бэклог — непрерывный пул; итерации — отдельный модуль
в будущем, если понадобятся.

## 2. Архитектура: ядро + модули

Два слоя:

- **Ядро платформы** — всегда в системе: пользователи, проекты, роли/права,
  реестр модулей, UI-каркас, канбан-доска, настройки инстанса.
- **Функциональные модули** — развиваются отдельно и подключаются к проекту.

**Модуль приносит с собой:**

- секции, права и бизнес-роли (§5);
- свои колонки канбан-доски (§6);
- свои MCP-инструменты (§7);
- настройки и собственные таблицы/миграции.

Модульность — основной принцип: систему растим модулями, ядро меняем
неохотно. Модуль описывается дескриптором в коде (не в БД): состав секций и
прав, роли, колонки, инструменты.

## 3. Стартовый набор модулей

Модули-стадии жизненного цикла задачи:

| Модуль | Ответственность |
|---|---|
| `backlog` | пул и приоритизация задач |
| `spec` | проработка: требования и критерии готовности |
| `dev` | разработка: ветки, ссылки на PR, статусы PR с git-хостинга (v2-9) |
| `review` | ревью кода |
| `qa` | прогоны и вердикты — функциональность v1 (§4) |
| `release` | релизные срезы и версии |

Детализация каждого модуля — задачами бэклога (§8), не этой спекой.

## 4. Модуль `qa` (наследование v1)

- Сессии прогонов «base/head» по коммитам, пары скриншотов «до/после»,
  вердикты тестировщика, библиотека кейсов с шагами, markdown-сводка.
- REST API v1 и MCP-сервер переезжают в модуль без изменения контрактов;
  инструменты становятся декларацией дескриптора.
- Роли v1 ложатся на стартовые роли v2 (§5, v2-17): owner → админ проекта,
  developer/tester → разработчик; REST/MCP работают от прав владельца ключа.

## 5. Пользователи, роли, права

- **Системная роль**: админ инстанса — создаётся setup-мастером, видит все
  проекты и модули, проходит любую проверку доступа.
- **Стартовые роли проекта** (v2-17): **админ** — настройки проекта,
  команда, модули; админов может быть несколько, админ назначает админов.
  **Разработчик** — доска и функциональность модулей, выпуск личных
  API-ключей. Канбан-доска открыта любому участнику. Сотрудник без роли
  не существует.
- **Ключи**: REST и MCP пускают только по ключу; ключ выпускает участник
  для себя, действует от его прав, живёт, пока он в проекте.
- **Проекты создаёт только админ инстанса** (v2-11, как в v1):
  самохостинг для своей команды, заведование проектами и предоставлением
  модулей — в одном месте.
- **Права = глаголы по секциям модулей**: `view` / `create` / `update` /
  `delete` + `settings` для конфигурации модуля. Состав секций —
  в дескрипторе модуля; на старте все глаголы модулей — у любого участника.
- **Модульные бизнес-роли** (v2-14) — отложенное расширение: дескриптор
  резервирует роли (`qa.tester`), спящие роли и фильтр назначаемых
  включаются отдельным релизом без смены API AccessService.
- **Индивидуальных грантов нет**: назначил роль — получил набор целиком;
  нестандартный случай = новая роль в коде, релизом.
- **Логика доступа — в одном месте** (AccessService); контроллеры,
  Livewire и Blade спрашивают `module.section.verb`, не решая сами.
- **Доступ = членство ∧ право** (v2-18): модули доступны всем участникам
  сразу, предоставления и включения нет. Без права — заглушка с пояснением.
- Релиз, убирающий роль, несёт миграцию, гасящую её строки в БД; неизвестный
  слаг отображается как есть, а не ошибкой 500.

## 6. Канбан-доска

- Доска проекта — ядро; колонки приходят из модулей-стадий,
  порядок — по жизненному циклу (§3). Одна доска на проект (v2-15).
- Номер задачи — `{KEY}-{n}` в пределах проекта: KEY задаётся при создании
  проекта (2–10 заглавных букв, уникален, не меняется); счётчик атомарный,
  без дыр; каждое перемещение — immutable-переход (кто, когда, откуда, куда).
- Фильтры по исполнителю и модулю, счётчики в колонках.
- Доступность колонок и действий — только через AccessService.

## 7. MCP и API

- **Разделение контрактов** (v2-12): MCP — чтение и ведение агента
  (задачи, стадии, критерии, результаты QA); запись — REST v2 (создание и
  перемещение задач, комментарии, артефакты). Паттерн v1: скриншоты
  грузились REST-ом, MCP отдавал данные и инструкции.
- Модуль может декларировать MCP-инструменты; сервер агрегирует их по
  модулям проекта. Вход — существующие ключи проектов.
- Инструменты `qa` — текущий набор v1 без изменений; новые инструменты
  задач — read-only (список, карточка, критерии, статус).

## 8. Процесс разработки

- Ветки: база — `v2`; feature-ветки от неё; слияние в `v2` — вручную через
  pull request. Коммиты — conventional, на английском (CONTRIBUTING.md).
- **Бэклог**: `docs/backlog/`, один файл — одна задача (схожие мелкие можно
  группировать в один файл). Один файл = одна ветка = одна сессия разработки;
  выполненный файл удаляется в той же ветке до PR.
- Имя файла: `NNN-slug.md`, нумерация сквозная. Формат: Цель / Контекст /
  Критерии готовности / Нерешённые вопросы.
- Миграция данных v1→v2 не делается (v2-16): v2 стартует с чистой базой,
  v1-инстансы остаются на v1.
- **Порядок работ** (первичное наполнение, обновляется по мере роста):
  001 движок → 005 задача → 006 каркас → 002 доска →
  014 drag-and-drop и фильтры → 007 `backlog` → 008 `spec` → 009 `dev` →
  015 статусы PR → 010 `review` → 011 привязка v1 к модулю → 016 перенос
  кода v1 → 012 `release` → 017 REST v2 → 013 MCP-агрегатор → 018
  MCP-инструменты задач → 019 комментарии → 020 уведомления → 021 дашборд →
  003 тёмная тема (в любой момент).

## 9. Дизайн-система

- Единственный источник токенов — `resources/css/app.css`; живая витрина —
  страница `/styleguide` (только dev-окружение, middleware `local.env`).
  Новый UI-паттерн сначала показывается на витрине, затем идёт в продукт.
- Светлая тема — oklch, акцент индиго; продуктовые токены `--fm-*`: тексты
  (`ink-2`, `muted`, `subtle`), линии, `row-hover`, `primary-soft`/`ring`,
  тени `xs–lg`, стопы фирменного градиента.
- Фирменный градиент: `.bg-primary`, `.btn-primary` и активный пункт
  навигации (`aria-current="page"`).
- Тёмная левая панель — класс `.app-sidebar` со собственной шкалой
  поверхностей (не глобальный тег).
- Цвета и тени в разметке — только токены; сырые значения запрещены.
- Шрифт — Golos Text, self-hosted переменный (без изменений из v1).
- Тёмная тема `femida-dark`: ретьюнинг под новую палитру — хвост (бэклог),
  до решения работает как есть.
