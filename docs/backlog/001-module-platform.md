# 001 — Модульный движок: реестр, дескрипторы, AccessService

## Цель

Движок модульности: реестр модулей с дескрипторами в коде и единая точка
проверки доступа. Без UI включения (это 004) и без сущности задачи (005).

## Контекст

Спека §2, §5. Сейчас в v1 роли плоские (админ инстанса / владелец проекта /
developer / tester), модулей нет, qa-функциональность в ядре.

## Критерии готовности

- Дескриптор модуля в коде: идентификатор, название, секции с правами
  (`view`/`create`/`update`/`delete`/`settings`), бизнес-роли (слаг с
  префиксом модуля: `qa.tester`), декларации колонок канбана и MCP-инструментов.
- Реестр (`ModuleRegistry`) собирает дескрипторы статически: `all()`, `find()`.
- Таблицы предоставлений и включений (`module_project`), данные пишет 004,
  движок читает.
- `AccessService` — единственная точка проверки: доступ = членство ∧
  предоставлен ∧ включён ∧ право; контроллеры, Livewire и Blade спрашивают
  `module.section.verb` через него (интеграция с Gate).
- Роли v1 (владелец проекта / developer / tester) выражены дескриптором
  `qa`; существующие проверки v1 проходят через AccessService, поведение v1
  не меняется.
- Без права по роли — заглушка с пояснением, не скрытая кнопка.
